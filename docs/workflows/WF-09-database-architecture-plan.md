## 一、业务职责与事实边界

WF-09 把用户真实提供的经历整理成履历条目。模块可以改善结构和表达，但绝对不能补造行动、结果、数字、奖项、工具或证明材料。

固定规则：

1. 用户本轮原话和已确认的 WF-09 历史条目是本模块的数据来源。
2. WF-09 没有强制上游工作流，不要求用户先完成画像、任务或成长复盘。
3. 即使其他模块中存在规划或任务，也不能把“计划做”自动当成“已经做”。
4. 用户要求夸大、伪造或冒领时必须拒绝，并帮助其基于真实内容改写。
5. 没有数字时 `指标=[]`；没有证明位置时 `evidence_locations=[]`，且质量状态至少为“缺少证明材料”。
6. 缺少关键事实时进入 collecting，每轮最多询问三个缺口，不生成完整履历条目。

## 二、关键事实门禁

生成完整条目前至少需要：

- 经历类型；
- 背景或目标；
- 用户本人角色或职责；
- 用户本人采取的行动。

结果、数字和证明材料不是生成草稿的绝对前置，但缺失时必须如实保留空数组并降低 `quality_status`，不得用常识补齐。

## 三、结构歧义的统一解释

原提示词存在三处需要在数据库版中固定的文字歧义：

1. confirmed 示例使用中文“条目”，确认规则写成 `confirmed.entrys`。数据库版统一使用正确英文键 `entries`，禁止再使用 `entrys` 或中文“条目”作为结构键。
2. 单条履历结构中的中文键“进球”按上下文明确解释为“目标”，数据库版统一使用中文键 `目标`。
3. 模块完成状态统一使用英文 `complete`；单条履历的质量状态仍使用原提示词规定的中文枚举。

这些调整只消除键名冲突，不改变业务含义。

## 四、单条履历结构基线

```json
{
  "entry_id":"R01",
  "entry_type":"课程项目|科研|竞赛|实习|社团|学生工作|志愿服务|其他",
  "背景":"",
  "目标":"",
  "角色":"",
  "动作":[],
  "工具":[],
  "结果":[],
  "指标":[],
  "evidence_locations":[],
  "resume_bullet":"",
  "detailed_story":"",
  "quality_status":"可直接使用|缺少量化结果|缺少证明材料|需要打磨",
  "missing_fields":[]
}
```

固定约束：

1. `entry_id` 在当前 confirmed entries 与 pending entry 中唯一，格式使用 `R01`、`R02` 等。
2. `resume_bullet` 使用“行动—方法—结果”结构，但只能写已有依据的结果。
3. `detailed_story` 只整理真实背景、行动、困难和结果。
4. 普通数组最多 5 项；confirmed 中 `entries` 最多保留 5 条，后续若确需更多容量再单独讨论，当前不增加数据库列。

## 五、draft 与 confirmed 结构基线

draft：

```json
{
  "pending_entry":{},
  "existing_entries":[],
  "摘要":""
}
```

confirmed：

```json
{
  "entries":[],
  "摘要":""
}
```

首次收集信息时可以在 `pending_entry` 中保存已经确认的部分事实和 `missing_fields`，但不能提前生成完整 `resume_bullet` 并进入 awaiting_confirmation。

## 六、状态机与动作规则

模块状态统一使用：

- `not_started`
- `collecting`
- `awaiting_confirmation`
- `complete`
- `cancelled`
- 明确澄清或安全拒绝时允许 `current_status="clarification_needed"`

动作规则：

1. 信息不足：保存部分事实草稿，status=collecting，最多追问三个缺口。
2. 信息完整：生成完整 pending entry，status=awaiting_confirmation。
3. confirm：仅当 pending entry 非空且完整时，将其追加到 confirmed.entries，保证 entry_id 唯一，清空 draft，status=complete，追加完成标记 WF-09，next_workflow=WF-12。
4. modify：只修正用户明确指出的事实或表达，不改变未被指出的事实。
5. cancel：只清空当前 draft，保留 confirmed.entries，status=cancelled。
6. 伪造请求：拒绝伪造，不把虚假内容保存为 draft 或 confirmed。

## 八、WF-09 模块表字段基线

建议表名：`wf09_resume_asset_records`

| 字段 | 类型 | 默认值 | 用途 |
|---|---|---|---|
| `asset_status` | String | `not_started` | WF-09 当前模块状态 |
| `asset_draft` | String | `{}` | collecting 或 awaiting_confirmation 草稿 |
| `asset_confirmed` | String | `{}` | 用户已确认的履历条目集合 |
| `asset_version` | Integer | `1` | 模块记录版本 |
| `last_user_intent` | String | `未记录` | 用户本轮原话 |
| `warnings` | String | `[]` | 本模块警告数组的 JSON 字符串 |

六个字段是后续读取、初始化、统一重新读取、大模型输入、C01 输出和模块写回的固定合同。单条履历的所有业务字段都保存在 draft 或 confirmed JSON 中，不再拆成数据库列。

回复不写数据库，继续通过共享 `last_reply`、现有 N90 和唯一结束节点返回。

当前状态：业务基线、事实门禁、结构解释、状态机和六字段模块表已经整理；讯飞星辰平台尚未实际建表。
