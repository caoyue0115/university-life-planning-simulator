## 一、先读结论：当前真正采用的架构

系统不是让大模型携带和重写一份庞大的全局 JSON，而是采用以下职责分离：

1. **MAIN 只负责路由**：读取轻量路由表，判断用户本轮动作和目标工作流。
2. **每个 WF 有自己的业务表**：保存本模块的状态、草稿、确认结果和必要的模块字段。
3. **每个 WF 的大模型只做业务推理**：读取本模块需要的数据，只输出本轮增量结果，不直接操作数据库。
4. **第一个代码节点 C01 负责解析和校验模型输出**：把对象/数组重新压成字符串，供数据库 String 字段保存。
5. **业务数据库节点负责写本模块表**。
6. **第二个代码节点 C02 负责合并全局完成列表并递增路由版本**：不能让大模型直接覆盖 `completed_workflows`。
7. **路由数据库节点负责写回轻量路由状态**。
8. **所有工作流把最终回复写入共享会话变量 `last_reply`**，再汇入 `N90` 和唯一结束节点。
9. **回复不进入数据库**：数据库只保存需要跨轮记忆的结构化状态。

最终通用骨架如下：

```text
M03 MAIN 总分支器的 WF-XX 出口
  → WFXX_DB01_读取依赖状态（按需；例如读取 WF-01 画像）
  → WFXX_DB02_读取本模块状态
  → WFXX_本模块状态是否存在
      如果 → WFXX_DB04_读取当前模块状态
      否则 → WFXX_DB03_初始化模块状态 → WFXX_DB04_读取当前模块状态
  → WF-XX 大模型
  → WFXX_C01_解析模型输出
  → WFXX_解析是否成功
      如果
        → WFXX_DB05_更新模块状态
        → WFXX_C02_合并路由状态
        → （建议）WFXX_路由合并是否成功
            如果 → WFXX_DB06_更新路由状态
            否则 → 写入安全失败回复
      否则
        → 写入 C01 已生成的失败回复
  → WFXX_写入 last_reply（变量存储器）
  → N90 统一回复
  → 唯一结束节点
```

这是 WF-03～WF-12 的默认模板。个别模块可以多一个业务表查询或分支，但不得破坏职责分离。

## 二、旧文档中已经失效、不得继续照搬的结论

旧 WF-01 文档是阶段性记录，以下内容已被今天的实际搭建结果修正：

| 旧结论 | 当前正确结论 |
|---|---|
| 删除 N90，让唯一结束节点直接引用 WF-01 的 `reply` | **错误。**唯一结束节点无法同时固定引用多个 WF 的 reply。必须保留 N90/共享 `last_reply` 汇合方案。 |
| 成功分支直接进唯一结束节点 | **错误。**成功和解析失败都要先获得非空 reply，再写入共享 `last_reply`，然后进入 N90。 |
| 解析失败用独立消息节点即可 | 可以显示消息，但如果结束节点仍读取 `last_reply`，可能返回旧值。当前统一做法是让 C01 在异常时生成非空失败 reply，两条分支共用写入 `last_reply` 节点。 |
| 其他工作流必须先完成画像 | **已取消这个硬门槛。**用户明确要求进入某模块时应直接进入；有画像则个性化，无画像则用中性通用场景。 |
| WF-02 无画像必须退回 WF-01 | **已修正。**WF-02 已验证可以无画像直接开始第一个模拟事件。 |
| `completed_workflows` 暂不处理 | WF-02 已加入 C02 合并步骤，去重添加本模块，并生成下一版本号。此模式要推广到后续 WF。 |
| 大模型输出完整全局 state | **不再采用。**大模型只输出本模块增量字段；全局状态由数据库链路维护。 |
| 搭建到中途发现缺字段再加表字段 | **禁止。**必须先从旧提示词和输出契约盘点全部持久化字段，再一次性定表。 |

以后发生冲突时，以本手册的“当前正确结论”和画布中已跑通的 WF-02 为准。

## 三、数据库总体设计

### 3.1 数据库

- 数据库名：`university_planner`

### 3.2 轻量路由状态表

- 表名：`agent_runtime_states`
- 用途：MAIN 读取、各 WF 完成本轮后写回。

系统字段由平台自动生成：`id`、`uid`、`create_time`。

业务字段：

| 字段 | 类型 | 默认值 | 必填 | 用途 |
|---|---|---:|---|---|
| `schema_version` | String | `mvp-1.1` | 是 | 当前轻量状态协议版本 |
| `current_workflow` | String | `WF-01` | 是 | 当前模块 |
| `current_status` | String | `not_started` | 是 | 当前模块状态 |
| `next_workflow` | String | `WF-01` | 是 | “继续”时默认去向 |
| `completed_workflows` | String | `[]` | 是 | JSON 数组字符串 |
| `profile_status` | String | `not_started` | 是 | WF-01 画像状态摘要 |
| `state_version` | Integer | `1` | 是 | 路由状态更新版本 |

注意：

- `completed_workflows` 必须保存为数组的 JSON 字符串，例如 `["WF-01","WF-02"]`。
- 不得直接把它覆盖成单个字符串。
- 路由表不保存各模块的大型草稿。

### 3.3 WF-01 业务表

- 表名：`wf01_profile_records`

| 字段 | 类型 | 默认值 | 必填 |
|---|---|---:|---|
| `profile_status` | String | `not_started` | 是 |
| `profile_draft` | String | `{}` | 是 |
| `profile_confirmed` | String | `{}` | 是 |
| `profile_version` | Integer | `1` | 是 |

### 3.4 WF-02 业务表

- 表名：`wf02_virtual_university_records`

| 字段 | 类型 | 默认值 | 必填 | 说明 |
|---|---|---:|---|---|
| `simulation_status` | String | `not_started` | 是 | 本模块状态 |
| `simulation_draft` | String | `{}` | 是 | 三轮事件的进行中状态 |
| `simulation_confirmed` | String | `{}` | 是 | 用户确认后的结果 |
| `simulation_version` | Integer | `1` | 是 | 模块记录版本 |
| `last_user_intent` | String | `未记录` | 是 | 用户本轮原话 |
| `warnings` | String | `[]` | 是 | JSON 数组字符串 |

两个重要细节：

1. 平台必填字段不能依赖“空字符串”选项。`last_user_intent` 的默认值和初始化值可手动输入 `未记录`，运行后再被真实输入覆盖。
2. JSON 内容不是在建表时展开成大量列。建表和初始化只放 `{}` 或 `[]`；真实结构由 WF-02 大模型输出，经 C01 转成字符串，再由 DB05 写入。

### 3.5 WF-03～WF-12 的建表原则

每个模块单独建一张业务表。推荐命名：

```text
wf03_<module>_records
wf04_<module>_records
wf06_<module>_records
...
wf12_<module>_records
```

建表前必须完成“字段盘点”，顺序不可颠倒：

1. 找到该 WF 当前正在使用的完整系统提示词和用户提示词。
2. 列出旧状态里该模块的全部字段。
3. 标出哪些字段需要跨轮保留。
4. 标出草稿、确认结果、状态、版本、用户原话、警告等字段。
5. 先确定大模型最终输出契约。
6. 再确定 C01 输出。
7. 再反推数据库字段。
8. 一次性建表，不允许搭到一半再随意补字段。

每张业务表通常至少包含：

| 通用字段 | 推荐类型 | 默认值 |
|---|---|---:|
| `<module>_status` | String | `not_started` |
| `<module>_draft` | String | `{}` |
| `<module>_confirmed` | String | `{}` |
| `<module>_version` | Integer | `1` |

是否需要 `last_user_intent`、`warnings` 或其他独立字段，必须根据该模块原提示词逐项确认，不能机械照抄 WF-02。

### 3.6 建表前必须填写的字段映射工作表

每开始一个新 WF，另一个 Agent 必须先完成下表，得到用户确认后才能让用户建表：

| 原提示词/旧状态字段 | 业务含义 | 是否跨轮需要 | 存储位置 | 数据库类型与默认值 | 模型输出字段 | C01 输出字段 | DB05 是否写入 |
|---|---|---|---|---|---|---|---|
| 示例：`module.status` | 模块状态 | 是 | 本模块表 | String / `not_started` | `<module>_status` | `<module>_status` | 是 |
| 示例：`module.draft` | 当前草稿 | 是 | 本模块表 | String / `{}` | `<module>_draft` | `<module>_draft_json` | 是 |
| 示例：`reply` | 本轮用户回复 | 否 | 会话变量 | 不建数据库字段 | `reply` | `reply` | 否，写 `last_reply` |
| 示例：`completed_workflows` | 全局完成列表 | 是 | 路由表 | String / `[]` | 不由模型直接输出 | C02 合并生成 | DB06 写入 |

填写规则：

1. 原提示词中每一个会被修改的状态字段都必须进入此表。
2. `reply`、冗长分析过程和知识库原文不得持久化。
3. 模块业务数据只能写本模块表；全局路由字段只能写路由表。
4. 如果某字段既不跨轮使用，也不参与查询、判断或最终确认，就不要为了“可能有用”而建列。
5. 表字段、模型输出、C01 输出和 DB05/DB06 引用必须逐项闭环，不能出现“模型输出了但无人保存”或“数据库列已建但无节点写入”。

### 3.7 不得根据模块名称臆造字段

目前只知道 WF-03～WF-12 的模块名称，不等于已经知道其完整业务状态。除了已验证的 WF-01、WF-02，不应直接给其他模块套上自创字段。

| WF | 模块名称 | 建表前必须取得 |
|---|---|---|
| WF-03 | 生存大冒险 | 当前完整系统提示词、用户提示词、旧输入输出、状态结构 |
| WF-04 | 五路径推荐 | 同上 |
| WF-06 | 主规划 | 同上 |
| WF-07 | 学期任务 | 同上 |
| WF-08 | 成长复盘 | 同上 |
| WF-09 | 履历素材 | 同上 |
| WF-10 | 决策与七天试错 | 同上 |
| WF-11 | 微习惯 | 同上 |
| WF-12 | 会话复盘 | 同上，并额外核对它需要读取哪些已完成模块摘要 |

拿到原提示词后，先做“业务规则无损清单 → 状态机 → 字段映射 → 输出合同”，再建表。缺少原提示词时应停在设计阶段，不能用 WF-02 的字段替代。

## 四、MAIN 路由的现行逻辑

### 4.1 MAIN 链路

```text
开始
  → DB01_读取路由状态
  → 路由状态是否存在
      如果 → DB03_读取当前路由状态
      否则 → DB02_初始化路由状态 → DB03_读取当前路由状态
  → N01 路由大模型
  → N02 变量提取器
  → M03 MAIN 总分支器
  → 对应 WF
```

### 4.2 N01 的职责边界

N01 只输出：

```json
{
  "target_workflow": "WF-02",
  "route_reason": "用户明确要求进入虚拟大学",
  "user_action": "jump",
  "requested_jump": "WF-02",
  "skip_current": false
}
```

不得输出画像、业务结果或完整 state。

### 4.3 已确认的新路由规则

1. 用户明确指定模块时，应路由到该模块。
2. `profile_status` 不再是进入其他模块的硬门槛。
3. 有确认画像时，业务 WF 可用于个性化。
4. 没有画像、画像为空或解析失败时，业务 WF 使用中性通用场景，不得强迫用户先回答画像问题。
5. 待确认草稿保护仍然保留：用户没有明确跳过当前待确认内容时，应留在当前模块。
6. `confirm`、`modify`、`cancel`、`answer` 仍路由到当前工作流。
7. `continue` 只在当前模块完成后进入 `next_workflow`。
8. WF-05 不存在，任何节点和提示词都不得输出 WF-05。

### 4.4 状态词兼容

历史上 WF-01 使用过 `completed`，WF-02 当前合同使用 `complete`。在全面统一前：

- N01 必须把 `complete` 和 `completed` 都视作终态。
- 新 Agent 不得在搭单个 WF 时顺便全局改状态拼写。
- 新 WF 应先按其原始业务合同做最小迁移；如要统一状态值，必须另开一次全局变更并同时改提示词、C01、分支条件和测试。

## 五、科大讯飞平台的真实配置规则

这些不是通用工作流平台的猜测，而是当前星辰界面已经确认的操作约束：

1. 数据库节点选择 **“表单处理数据”**。
2. 查询、新增、更新是不同处理模式。
3. “新增数据”节点中，所有业务字段都会出现，必须逐项填写；不能只依赖表默认值。
4. 查询和更新必须设置“数据范围”。
5. 引用上游变量后，平台会自动携带类型，不需要再手填 `Array<Object>`。
6. 代码节点输入参数名使用下划线，例如 `model_output`、`route_state_rows`，不要使用带空格的名称。
7. 分支器比较布尔值时使用真正的 Boolean `true`，不能填写字符串 `"true"`。
8. 每个分支出口都必须有去向，避免悬空。
9. 数据库节点默认输出 `isSuccess`、`message`、`outputList` 通常保持不变。
10. 平台只有普通结束节点；当前系统使用唯一结束节点，因此必须先通过共享 `last_reply` 汇合。
11. `profile_version > 0` 或 `<module>_version > 0` 只表示“找到已初始化记录”，不代表用户已确认内容；是否确认要看对应 `confirmed` 是否为空以及状态字段。
12. 当前查询条件依赖平台按 `uid` 自动隔离记录，仍需用两个账号或两个用户会话做隔离验证。

## 六、搭建一个新 WF 的逐节点标准流程

以下用 `WF-XX` 表示任意新模块。另一个 Agent 必须一次只指导用户搭一个节点；每个节点搭完并确认后再给下一步。

### 第 0 步：冻结原始业务规则

在动画布前先做四件事：

1. 取得该 WF 当前完整系统提示词和用户提示词。
2. 列出必须无损保留的业务细节：开始、回答、确认、修改、取消、安全限制、输出规则。
3. 标记哪些旧规则属于旧的“大 JSON 状态架构”，只迁移存储方式，不改变业务含义。
4. 输出一份字段清单、状态机和最终 JSON 合同，让用户确认后再建表。

**禁止**重新发挥一套“更好”的业务逻辑。默认目标是数据库化迁移，不是产品重写。

### 第 1 步：建立模块业务表

先创建所有字段。系统字段不动，业务字段全部设好类型、默认值和必填要求。

如果字段是对象或数组：

- 对象保存为 String，默认 `{}`。
- 数组保存为 String，默认 `[]`。
- 不把 JSON 子字段拆成数据库列，除非后续确实需要独立查询。

### 第 2 步：读取依赖数据

如果模块会用画像，在 M03 的 WF-XX 出口后先接：

```text
WFXX_DB01_读取画像状态
```

配置：

- 数据表：`wf01_profile_records`
- 模式：查询数据
- 数据范围：`profile_version > 0`
- 查询上限：`1`
- 结果字段：至少包含该 WF 真正需要的 `profile_confirmed`；只有业务明确使用草稿时才读 `profile_draft`

注意：无画像不能拦截模块。大模型提示词中要写明：有有效确认画像则使用；无画像则使用中性通用场景。

如果模块还依赖其他已确认模块结果，按同样方式增加只读查询节点，但只读取真正需要的关键字段。

### 第 3 步：读取本模块状态

新增：

```text
WFXX_DB02_读取模块状态
```

配置：

- 数据表：本模块业务表
- 处理模式：查询数据

### 第 8 步：C01 解析模型输出

新增代码节点：

```text

```

输入：

| 参数 | 引用 |
|---|---|
| `model_output` | WF-XX 大模型的 `output` |

C01 的职责：

1. 确认输入是字符串。
2. 去掉可能出现的 Markdown 代码围栏。
3. `json.loads()` 解析顶层对象。
4. 校验必填字段、状态值和工作流编号。
5. 把 draft、confirmed、warnings 等对象/数组用 `json.dumps()` 转为紧凑字符串。
6. 成功返回 `parse_ok=true`。
7. 失败时返回 `parse_ok=false`、具体 `error_message`，并同时返回一个**非空、可展示的安全失败 reply**。

失败 reply 推荐：

```text

```

### 第 11 步：C02 合并路由状态

新增：

```text
WFXX_C02_合并路由状态
```

输入：

| 参数 | 引用 |
|---|---|
| `route_state_rows` | MAIN 的 DB03 当前路由记录 `outputList` |
| `completed_workflow_add` | C01 的同名输出 |

建议使用下面的稳定模板；不要机械复制旧 C02 未测试代码：

```python
# -*- coding: utf-8 -*-
import ast
import json


def parse_value(value):
    if not isinstance(value, str):
        return value

    text = value.strip()
    if not text:
        return value

    try:
        return json.loads(text)
    except Exception:
        try:
            return ast.literal_eval(text)
        except Exception:
            return value


def main(route_state_rows, completed_workflow_add):
    try:
        rows = parse_value(route_state_rows)

        if isinstance(rows, dict):
            rows = [rows]

        if not isinstance(rows, list) or not rows:
            raise ValueError("route_state_rows 中没有有效路由记录")

        row = parse_value(rows[0])
        if not isinstance(row, dict):
            raise ValueError("路由记录必须是对象")

        completed = parse_value(row.get("completed_workflows", []))
        if completed in (None, ""):
            completed = []
        if not isinstance(completed, list):
            raise ValueError("completed_workflows 必须是 JSON 数组")

        clean_completed = []
        for item in completed:
            if isinstance(item, str):
                item = item.strip()
                if item and item not in clean_completed:
                    clean_completed.append(item)

        workflow_to_add = completed_workflow_add
        if isinstance(workflow_to_add, str):
            workflow_to_add = workflow_to_add.strip()

        if workflow_to_add:
            if workflow_to_add not in clean_completed:
                clean_completed.append(workflow_to_add)

        raw_version = row.get("state_version", 1)
        raw_version = parse_value(raw_version)
        try:
            state_version = int(raw_version)
        except Exception:
            state_version = 1

        return {
            "merge_ok": True,
            "error_message": "",
            "completed_workflows_json": json.dumps(
                clean_completed,
                ensure_ascii=False,
                separators=(",", ":"),
            ),
            "state_version_next": state_version + 1,
        }

    except Exception as error:
        return {
            "merge_ok": False,
            "error_message": str(error),
            "completed_workflows_json": "[]",
            "state_version_next": 1,
        }
```

C02 输出：

| 变量 | 类型 |
|---|---|
| `merge_ok` | Boolean |
| `error_message` | String |
| `completed_workflows_json` | String |
| `state_version_next` | Integer |

```json
      "completed_workflows": "[\"WF-01\"]",
      "state_version": 1

}
```

期望结果：

- `merge_ok = true`
- `completed_workflows_json = ["WF-01","WF-02"]`（实际为紧凑 JSON 字符串）
- `state_version_next = 2`
- `error_message` 为空

只有代码节点独立测试通过后，才测试完整工作流。

### 第 13 步：建议增加 C02 成功保护

- 否则：不要写路由表；进入一个单独的“路由合并失败写入”变量存储器，把 `last_reply` 写成固定安全错误提示，再进 N90。

### 第 15 步：统一写入 last_reply

DB06 后接一个变量存储器：

```text

```

只写一个会话变量：

| 变量 | 值 |
|---|---|
| `last_reply` | `WFXX_C01_解析模型输出.reply` |

解析失败分支也进入同一个变量存储器，因为 C01 异常时已经提供了非空安全 reply。

然后：

```text

```

不要新增“回复数据库”，也不要让每个 WF 直接占用唯一结束节点。

### 第 16 步：理解两层写回的顺序与失败边界

正常顺序必须是：

```text
C01 解析成功
→ DB05 写本模块业务状态
→ C02 合并路由状态
→ DB06 写轻量路由状态
→ 写入 last_reply
→ N90
→ 唯一结束节点
```

原因：模块草稿和确认结果属于本模块表；当前模块、下一模块、完成列表和路由版本属于路由表。两者不能混在一个数据库节点里。

星辰工作流中的两个数据库写入不是一个数据库事务，因此存在部分成功的可能：

- DB05 失败：不能继续 DB06，也不能告诉用户状态已经保存。
- DB05 成功但 DB06 失败：模块数据可能已保存，但全局路由仍旧；应返回安全提示并在下一轮重新读取后恢复，不能重复覆盖草稿。
- DB06 成功后：才可以发送本轮正常业务 reply。

如果平台允许按 `isSuccess` 分支，建议在 DB05、DB06 后各加成功判断；具体比较类型必须先用节点调试确认，不能凭经验猜它返回 Boolean 还是字符串。

## 七、WF-02 已跑通的实际业务逻辑

WF-02 用三个连续事件完成压缩版大学模拟：

1. 第一个事件：课程与社团/项目的资源冲突。
2. 第二个事件：科研、比赛与实习的冲突。
3. 第三个事件：目标收敛与机会成本。

每轮会把当前题目、选项和历史选择写入 `simulation_draft`。用户下一轮只说“我选 A，因为……”时，WF-02 从数据库读回草稿，因此知道上一轮问的是什么，并推进到下一个事件。

第三轮完成后进入 `awaiting_confirmation`，生成：

- `graduation_snapshot`
- `main_risks`
- `restart_advice`

用户确认后：

- draft 清空为 `{}`。
- confirmed 保存最终结果。
- `simulation_status` 和 `current_status` 进入完成态。
- `completed_workflow_add = "WF-02"`。
- `next_workflow = "WF-12"`。

### 无画像直达规则

WF-02 最终提示词是在原有版本上做**最小修改**，只改变画像硬门槛：

1. 有可解析的非空 `profile_confirmed`：用于个性化，但不得改写画像。
2. 没有画像、画像为空或无法解析：使用中性通用场景，仍然直接开始事件一。
3. 不得把 `current_workflow` 或 `next_workflow` 改回 WF-01。
4. 不得仅因为缺画像设置 `clarification_needed`。
5. 不得追问学校、GPA、昵称、地点偏好等画像问题。

验证语句：

```text
直接进入模拟大学环节
```

正确结果：同一轮直接生成事件一及 2～3 个选项；不能再要求先完成画像。

下一轮验证记忆：

```text
我选 A，因为我更重视课程基础。
```

正确结果：进入事件二，而不是重做事件一。

## 八、提示词修改的固定方法

这是本次最重要的协作规范之一。

### 8.1 必须做最小修改

当用户给出正在运行的完整提示词后：

1. 以用户当前实际版本为唯一底稿。
2. 全文找出所有会影响目标的规则，不只改第一处。
3. 只替换必要位置。
4. 不擅自扩写、重构、改状态机或改输出结构。
5. 最后明确列出改了哪几处。
6. 给用户一份可以整体复制的最终完整提示词，而不是只给零散片段。

### 8.2 为什么“只改一处”也可能失败

例如画像硬门槛同时存在于：

- MAIN 路由规则；
- 多目标优先级规则；
- WF-02 自己的输入规则；
- WF-02 的开始和出题规则。

只删掉一句“需要画像”并不足够，其他条款仍可能把用户送回 WF-01。因此必须全文搜索所有同义约束，再做最小范围的成组替换。

### 8.3 不能把“最小修改”误解为“只改一行”

最小修改的意思是：修改所有与目标直接相关的位置，但不碰无关业务细节。既不能漏改，也不能借机重写整份提示词。

## 九、本次已经踩过的坑和预防规则

### 坑 1：建表后才发现少字段

WF-02 搭到中途才补 `last_user_intent` 和 `warnings`，导致返工。

预防：先冻结完整提示词和输出合同，再一次性建表。另一个 Agent 在给出建表字段前，必须完成字段交叉检查。

### 坑 2：把 JSON 数据误解为建表时输入的完整内容

数据库表只需要 String 字段和 `{}`/`[]` 默认值。真实 JSON 由大模型生成、C01 序列化、DB05 写入。

### 坑 3：把读取和初始化混成一个节点

查询节点只读取。不存在时必须走分支器，再由独立新增节点初始化，之后重新读取。

### 坑 4：用版本大于零判断“已确认”

`profile_version > 0` 只说明记录存在。是否确认必须检查 `profile_confirmed` 和对应状态。

### 坑 5：让路由模型生成业务数据

路由模型只决定去哪个 WF 和识别动作。WF-02 模拟数据必须由 WF-02 自己的大模型生成。

### 坑 6：结束节点直接引用某个 WF 的 reply

一个结束节点不能静态引用所有 WF 的不同代码输出。正确方式是每条 WF 先写共享 `last_reply`，再进入 N90。

### 坑 7：把回复持久化到数据库

回复只需用于本轮展示，不需要长期保存。使用会话变量，不新建回复数据库字段。

### 坑 8：失败消息节点与 last_reply 冲突

如果结束节点读取 `last_reply`，独立消息节点之后可能仍返回旧值。当前标准是 C01 异常时生成非空失败 reply，再走统一变量存储器。

### 坑 9：代码报错后先改整条链路

WF-02 C02 曾出现通用 `Code execution failed`。正确诊断顺序是：

1. 保持连线不动。
2. 在代码节点自身输入测试里使用最小固定样例。
3. 先确认代码能独立运行。
4. 再比较真实上游输入格式。
5. 最后才考虑加保护分支或改连线。

### 坑 10：代码只兼容理想输入类型

星辰节点可能传入 JSON 字符串、对象或数组。C02 应兼容这些输入形式，并在 try/except 中返回可观察的 `error_message`，不能只让平台报通用失败。

### 坑 11：布尔 true 写成字符串

分支器必须使用 Boolean `true`。字符串 `"true"` 不相等。

### 坑 12：擅自扩大提示词修改范围

用户要求取消画像硬门槛时，曾出现一版扩写过多的提示词。正确做法是回到用户当前原文，只改所有相关拦截位置，其余业务和输出完全保留。

### 坑 13：用画像作为所有模块的硬入口

这会让用户明明说“进入虚拟大学”，却连续被追问学校、GPA、昵称等。现行产品规则是画像可选增强，不是强制门槛。

### 坑 14：完成列表直接覆盖

不得让 DB06 写死 `["WF-XX"]`。必须读取旧数组、去重保留、按需追加，再写回。

### 坑 15：自动假定某个保护节点已经搭好

文档建议与画布现状必须区分。WF-02 C02 已单测通过，但 C02 后的 `merge_ok` 保护分支是否已经真正加入，需要现场核对。

## 十、交给另一个 Agent 的执行纪律

1. 一次只指导一个节点，不把后续十个节点同时扔给用户。
2. 用户说“已经搭好”后，直接进入下一个节点，不重复上一阶段。
3. 用户的闲聊不需要回应；只提取其中明确的技术问题或命令。
4. 不要声称已经查看到未实际查看的截图、提示词或画布配置。
5. 给代码前先核对星辰代码节点的输入名和输出类型。
6. 每段代码必须同时给：输入变量、输出变量、单节点测试输入、预期输出。
7. 代码单测通过前，不让用户修改整条连线。
8. 在建议删节点前，先确认替代路径已经完整连接并能返回非空 reply。
9. 不把“推荐优化”伪装成“当前已完成”。
10. 不在模块迁移中顺手重构 MAIN、其他 WF 或全局状态词。
11. 如果用户要求最小修改，必须回到其当前原文逐条对照，不能凭记忆重写。
12. 每个 WF 完成后更新本手册中的“已验证状态”和实际节点清单。
